# 上游合并记录

本目录记录二开仓库对 [getpaseo/paseo](https://github.com/getpaseo/paseo) 每个上游发布标签的处理结果:哪些提交合并了、哪些冲突以及如何解决、哪些丢弃以及为什么。

**一个上游标签一个文件**,全部放在 [tags/](tags/) 子目录下,文件名即标签名,例如 [tags/v0.5.1.md](tags/v0.5.1.md)。

## 为什么需要这个目录

二开采用**挑选式合并**,不做整版跟随。这带来两个 Git 无法回答的问题:

1. **分诊水位线在哪。** `git describe` 和"落后多少提交"都不反映真实进度——挑选时做过适配的提交 patch-id 与上游不同,按 SHA 或补丁等价统计都会严重低估覆盖率。
2. **某个上游提交为什么没进来。** 是没看过,还是看过之后判定与二开功能冲突而丢弃?没有记录就只能每轮重新判断一次。

## 当前水位线

| 项目                 | 值                                     |

| 已完成分诊的上游范围 | `v0.7.0` 提交 `4e60c2880` 及以前       |
| 已建立记录的最早标签 | `v0.5.0`（2026-08-23，补记）           |

`v0.7.0` 正式版已经取代同版本的三个 beta 标签。本地 `upstream` 抓取配置明确排除 `refs/tags/v0.7.0-beta.*`，只保留正式 `v0.7.0`；原先两份 beta 分诊记录已经无损合并到 [v0.7.0](tags/v0.7.0.md)，后续不得恢复本地 beta 标签或重新建立 beta 台账。

`v0.4.0` 及更早的标签**不建立记录**,视为已完成、不再追溯。

[v0.5.0](tags/v0.5.0.md) 是**补记**:当初已按挑选式合并处理过,但没留记录。补记时不逐条重放 184 个提交,而是按上游功能清单核对二开代码的实际状态,重点找出"当初跳过、现在挡住新版本合并"的项。

## 记录约定

- **一个标签一个文件**,即使该标签只有发布提交也建文件,写明"无需合并"。
- 只记录实质提交。`chore(release): cut *`、`docs(changelog)*`、`fix: update lockfile signatures and Nix hash` 属于发布噪音,在文件头写明排除数量即可,不逐条列出。
- **每个提交必须用白话写清楚它改变什么功能**,让人不看代码就能判断要不要合。技术细节只在影响判断时才写。每条固定三段:

  | 段落             | 写什么                                                                    |
  | ---------------- | ------------------------------------------------------------------------- |
  | **做什么**       | 用户能看到的变化。修复类写"原本会怎样、修完怎样",功能类写"多了什么能力"。 |
  | **对二开的影响** | 会不会跟现有二开功能打架,以及能不能直接 cherry-pick(见下方"前置依赖")。   |
  | **建议**         | 合并 / 需审计 / 待决策 / 丢弃,加一句理由。                                |

- **丢弃必须写原因**,不能只写"跳过"。原因要能让半年后的人不必重新读代码就理解判断依据。
- **冲突必须写解决方式**,并注明是否影响 [fork-features.md](../docs/fork-features.md) 中的条目。若某次合并改变了二开功能行为,必须在同一次交付中改写该功能条目。
- 合并完成后回填二开侧的提交号,使记录可追溯到实际代码。

## 状态词汇

| 状态           | 含义                                             |
| -------------- | ------------------------------------------------ |
| **待处理**     | 已分诊并给出建议,尚未动手                        |
| **已合并**     | 干净合并,无冲突                                  |
| **冲突已解决** | 有冲突,已解决并验证                              |
| **已丢弃**     | 判定不合并,原因已记录                            |
| **待决策**     | 需要仓库所有者拍板,不由执行者自行选择            |
| **部分合并**   | 该标签已合并明确选择的功能，其他条目仍按记录保留 |

## 右侧面板:不跟随上游结构

**这是一条长期策略,适用于今后每一次分诊。**

二开已经完全重构了右侧 Git 面板([fork-features.md](../docs/fork-features.md) 功能 16),并改造了文件面板(功能 21)。上游在这块的**结构性改动一律不跟随**:

- 不合并 Side 面板、Explorer 侧栏及其衍生的布局迁移、打开位置路由、面板宿主化重构。
- 不合并针对上游自己那套更改列表、差异视图、拉取请求面板的内部修复——二开的实现是另一套代码,上游的补丁既打不上也不解决二开的问题。

**今后只看一件事:上游有没有引入右侧面板的新能力。** 有的话单独评估要不要在二开自己的实现上做一个,而不是合并上游的提交。分诊时把这类条目记成"新能力候选",写清楚它给用户带来什么,不必分析文件冲突。

**例外:** 服务端支撑(Git 命令层、检出状态、拉取请求轮询)不属于右侧面板 UI,照常按价值分诊。二开的 Git 面板消费的正是这些接口。

**另一类例外:** 上游常把不相干的改动压进同一个提交。右侧面板提交里如果夹带了独立能力,单独摘出来评估——例如 `v0.6.0` `c914bcb44` 里的自定义窗口控件。

## 分诊风险等级

风险等级来自**改动文件与 [fork-features.md](../docs/fork-features.md) 功能落点的交集**,是冲突可能性的估计,不是代码级审阅结论。等级高只意味着需要人工审计,不等于一定冲突。

| 等级   | 含义                                                |
| ------ | --------------------------------------------------- |
| **低** | 不触及任何二开功能落点,预期干净合并                 |
| **中** | 触及二开文件,但改动区域大概率不重叠                 |
| **高** | 直接改动二开功能的核心文件,必须逐条对照功能清单审计 |
