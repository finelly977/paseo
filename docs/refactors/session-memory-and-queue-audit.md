# 会话加载、内存驻留与队列审计

审计日期：2026-10-30。范围是当前二开 `main` 工作副本，不涉及上游版本比较。

本次只研究和验证，没有修改产品逻辑、用户设置或真实会话数据，没有停止或重启主守护进程。此前未提交的安装器修改保持原样。

后续处理：同日已按用户要求实现运行时释放后的服务端和客户端缓存清理，释放后的状态见 [agent-lifecycle.md](../agent-lifecycle.md)。下文保留修复前的审计证据，不再代表该释放缺口仍未处理。长会话写入、加载目标和分页另见 [Codex CLI 对照研究](codex-history-storage-and-pagination.md)，并发调度按用户要求暂不调整。

## 结论

当前存在可复现的问题，单纯调低“加载对话数”或“历史内存上限”无法解决。

最需要处理的是：长会话每批持久化都重做完整 JSON、服务端历史缓存没有回收预算、历史阅读窗口与客户端裁剪冲突，以及历史请求缺少统一的并发和优先级管理。四条路径可以同时发生，使一次历史加载既产生进程恢复和大对象分配，又反复进行全量投影、网络回传和客户端全局扫描。

同一会话的初始化去重、前后台事件顺序和空闲进程回收并非完全失效。本机日志能看到正常回收，相关测试也通过。问题集中在这些局部机制之间缺少一致的资源边界。

| 工作区与部分标签保留   | 工作区保留 3 个；标签保留路径以 3 为目标               | 界面组件挂载；修改中的标签可以豁免     | 客户端全局 Store、后台进程、服务端历史缓存               |

## 2. 本机样本与验证边界

对 `C:\Users\qq134\.paseo` 做了只读采样：

- 会话记录 362 条，其中归档 292 条、未归档 70 条。
- 持久时间线文件 212 份，JSON 合计约 290.8 MiB。
- 未归档会话对应的 70 份时间线约 221.2 MiB。
- 最大文件 42.88 MiB，包含 6,172 条规范记录、227 条用户消息，其中工具记录 4,944 条。

这些是磁盘记录和采样时的数据，不代表 362 个进程正在运行，也不代表全部时间线都已经被主守护进程加载。其他会话仍在更新，所以文件总量会变化。最大样本只有 227 轮，却已有约 43 MiB JSON，说明 500 轮预算不能换算成固定内存大小。

在隔离 Node 进程中，通过当前真实存储实现只读载入最大文件：

- 载入、校验和生成调用方快照约 256 毫秒。
- 在载入后仍持有调用方快照的测量点执行 GC，相对基线增加约 136 MiB 堆内存；该阶段还可能包含尚未退出的异步调用临时对象。
- 丢弃调用方快照、让出事件循环并再次 GC 后，相对基线仍增加约 70 MiB。

这是隔离基准，不是正在使用的守护进程堆快照；没有测量 Electron、所有提供方进程或生产峰值。不能把磁盘大小直接当成实际内存占用。

## 3. P1：持久化每批都复制并重写完整历史

`DurableTimelineBuffer` 默认按 25 毫秒窗口合并待写记录，但最终调用的 `FileAgentTimelineStore.bulkInsert()` 会：

1. 深复制当前完整文档。
2. 加入新记录并校验完整文档。
3. 通过 `writeJsonFileAtomic()` 序列化全部 JSON，再写临时文件和替换原文件。

25 毫秒是合并窗口，不是工作量上限，也不意味着长文档能在 25 毫秒内完成。

使用本机 42.88 MiB 样本，注入已有写入端口，只序列化、不实际落盘，每批增加一条很短的助手消息，三批分别耗时：

- 232.53 毫秒
- 232.60 毫秒
- 207.20 毫秒

三批生成的待写入 JSON 合计 128.64 MiB，原文件大小和修改时间均未变化。测量不包含磁盘写入和重命名耗时。

深复制、校验、序列化发生在 Node 事件循环上。一条长会话产生工具事件时，会拖延同一守护进程上其他会话的历史、状态和消息响应。多个会话同时写入又会加重分配和 GC。待写数组没有按总字节数或积压时长设置背压。

这条路径已经具有足够大的单批成本，是需要优先处理的卡顿来源；尚未通过生产 CPU 跟踪量化它占用户某次具体卡顿的比例。

## 4. P1：释放运行时没有释放完整历史；搜索也会扩大缓存

服务端有两份不同用途的历史容器：

- `AgentManager.timelineStore`：已加载智能体的规范时间线。
- `FileAgentTimelineStore.documents`：从磁盘读入的完整 JSON 文档缓存。

`prepareAgentForClosure()` 会移除运行时和会话订阅，但不移除前一份历史。后一份缓存没有数量、字节、TTL 或 LRU 限制，只有删除真实会话文档时才删除对应缓存。归档保留磁盘历史，也不会借此自动清除该文档缓存。

正文搜索经过 `getTimelineForSearch()` 调用同一持久存储的完整读取接口。搜索虽然限制为两个扫描任务、不会恢复提供方进程，但扫描过的文件仍进入常驻缓存。取消查询只停止继续扫描，已完成的读入不会回收。

在两个合成文件的隔离验证中，搜索结束且无任何命中后，原存储实例仍返回缓存记录；改写测试文件后，新实例读到空文档，原实例继续返回旧缓存。这证明搜索任务结束不等于缓存生命周期结束。测试仅改写 `.output` 内合成文件。

本机未归档历史约 221 MiB。如果无命中搜索遍历这批候选，涉及的完整时间线会逐条读入，而非仅保留最后显示的 100 个搜索摘要。该条件说明潜在扩大范围，不代表本机生产进程已经发生了完整遍历。

## 5. P1：当前历史阅读窗口会被总预算反向裁掉

客户端按“当前焦点优先，其次最近打开时间”分配轮数。实际裁剪始终保留最近部分，不知道用户当前正在阅读哪段历史。

隔离 Store 测试确认：

1. 当前会话预算为 2 轮。
2. 向前补载后暂有 3 轮。
3. 执行总预算后，新补进来的最旧一轮立即被删除。
4. 起始游标从旧位置重新前移。

这意味着触及预算后，上滚可能持续请求同一段旧记录，加载结束却留不住内容。降低总上限，会更早触发这种冲突。

设置也允许“单会话打开目标 50 轮、全局总上限 1 轮”这类组合：网络继续按较大目标加载，客户端按较小预算丢弃。两个设置之间没有共同的有效加载预算。

当前焦点只记录一个会话，并不等于所有可见分栏。其他可见分栏可能在总预算分配中被当成普通旧会话。该分配规则由代码确认；没有在真实多分栏界面复现具体抖动，不能把它当成本次用户所有滚动问题的唯一原因。

## 6. P1：默认 50 轮可能变成大量串行请求

首屏限制 40 条投影记录，可以避免一次提交大量内容；后续同步器会继续每页 40 条，向前补齐设置要求的轮次。对于命令密集的会话，50 轮可能远大于 50 条展示项。

使用当前真实投影与分页函数，对本机最大样本模拟加载最近 50 轮：

- 共需 40 次请求，包含首屏和后续 39 页。
- 返回条目的 JSON 合计约 11.14 MiB，不含额外协议和索引开销。
- 后续补页串行执行，网络往返时间会逐页累加。

服务端读取一个尚未加载的会话时，会先经过 `ensureAgentLoaded()` 恢复提供方运行时，并读取、核对完整规范历史。客户端“只取 40 条”的分页没有把主机端冷载入变成按需分页。这里是每个会话首次需要恢复，并非 40 页创建 40 个运行时。

含工具生命周期的分页经常需要读取完整时间线再做投影；每次请求还重新构建完整对话索引。索引版本可以减少网络重复传输，但判断版本前仍重做索引，不是服务端计算缓存。

同步器的自动补页也没有与用户主动上滚共用统一的优先级队列。相同请求可去重，不同游标的自动补页与手动请求仍可重叠。

## 7. P1：没有统一的历史加载并发、取消和优先级

当前存在同会话初始化 Promise 去重、相同请求去重和订阅成员变更串行化；这些机制都有作用，但不限制不同会话同时加载。

初始化或运行中的后台会话会加入时间线订阅，并进入与可见会话相同的历史追赶路径。隔离同步器测试确认：12 个后台运行会话加入后，在任何请求完成前，12 个历史请求全部已经发出。

当前没有“前台主动阅读 > 前台首屏 > 后台补齐”的优先级，也没有共享的历史请求并发额度。快速切换会话时，30 秒订阅宽限还会让近期会话暂时同时处于投递集合中。

切换或取消同步时会让旧 generation 失效，阻止旧循环继续请求下一页；已发出的 RPC 没有传输级取消，服务端的恢复、读取和投影仍会执行，响应也先经过统一历史应用入口。这是取消继续工作和取消正在工作之间的差别。

运行时层面同样没有总驻留数量或内存软限额。当前是固定空闲 TTL，活动回合、后台任务、权限交互、可见会话和活动定时任务受到保护，`error` 与 `internal` 也不会由这条空闲规则回收。不能通过一律关闭旧进程来修复，否则会中断真实任务。

## 8. P2：客户端预算不是完整内存预算，执行位置也偏重

已验证的边界：

- 轮次以用户消息计数，一轮中大量工具结果和长文本没有字节预算。
- 没有用户消息边界的独立缓存可以按 0 轮计算；测试中 100 万字符的后台助手记录不占用轮数分配。
- 正在生成的 head 不被裁剪；在四个会话的活动 head 中各加入待确认用户补充后，3 轮总预算仍保留 4 条用户消息。不能直接丢弃这些消息，应将活动工作单列预算。
- 完整导航索引明确不参与正文裁剪。测试中后台正文被淘汰后，100 条导航索引仍驻留。这符合当前功能约定，但不应把正文上限解释为全部内存上限。

`enforceConversationHistoryMemory()` 每次都会收集所有 Host 的 head 与 tail、拼接临时数组、扫描轮数、排序并再次检查裁剪。它在历史每页应用后以及实时批次提交后调用。缓存越多，一个会话的增量越可能触发与其他会话总内容相关的工作量。

这条全局扫描开销已由代码确认，尚未用真实浏览器 CPU 跟踪分离其耗时，不能直接给出占帧比例。

## 9. P2：诊断会漏报仍驻留的历史

`AgentManager.getMetricsSnapshot()` 仅遍历当前有运行时的 `agents`，统计对应时间线；没有计入已关闭运行时留下的时间线，也没有计入持久存储文档缓存。

合成搜索验证中，没有任何运行时，诊断的智能体数和时间线条目数均为 0，但持久文档缓存已经有数据。只看“已加载会话数下降”或该时间线计数，会误以为历史内存已经归还。

需要分别观察：目录记录数、提供方运行时数及进程内存、规范时间线缓存、持久文档缓存、客户端正文与索引、挂载面板、加载/写入积压。不能合并成一个“会话数”。

## 10. 消息队列与历史队列应分开理解

目前没有一个覆盖全部会话的统一 FIFO 队列。

- 每个智能体的提供方事件有串行 Promise 链。
- 每个智能体的持久化有顺序与合批。
- 同一智能体的活动回合有互斥保护。
- 不同会话的加载和运行可以并发，不受统一驻留预算限制。
- 输入框排队消息保存在当前客户端的 `queuedMessages` 内存 Map 中，按对应会话结束事件尝试发送；它不是主机持久任务队列，不会跨设备共享，客户端进程结束也没有恢复契约。
- 定时消息另有主机持久化机制，不能与普通输入框排队消息混为一谈。

自动发送失败会把消息放回队首；本轮没有证据认定已成功确认的消息会丢失，也没有端到端复现多客户端发送竞争。不能仅凭局部队列结构就把它们写成已确认缺陷。

## 11. 建议处理顺序

### 第一批：先去掉确定的大工作量和阅读冲突

1. 将历史持久化改为有界的分段或追加提交，避免每批深复制与重写整个会话。保留现有文件存储契约、顺序、原子提交与失败重试；存储格式调整需要单独设计，不能顺手替换成数据库。
2. 给服务端规范时间线和持久文档缓存分别设置数量与字节预算。搜索使用不污染热缓存的读取路径；回收运行时后归还可重建的大对象，只保留身份、持久游标和轻量摘要。
3. 将历史阅读窗口与缓存淘汰分开。保护用户正在看的区间和全部可见分栏；已到上限时淘汰其他会话，或移动阅读窗口，不能刚补进来就删除同一页。单次加载目标与总预算需要协调。

### 第二批：建立有界加载调度

1. 历史 RPC 使用共享并发额度，前台用户请求优先，后台自动补齐低优先。具体额度应由桌面、移动和远端延迟基准确定，不能凭感觉再写一个数字。
2. 自动补载与用户上滚共用同会话调度和游标所有权，切换后取消尚未开始的任务；正在执行的工作在明确检查点停止，不强制终止共享进程。
3. 将“恢复可交互运行时”与“只读历史查询”分离，已有权威历史可直接按页读取；需要与原生历史核对时单独进行，保证完整历史和回合身份不退化。
4. 对后台运行会话保留必需的实时投递与完整主机记录，不默认给每个客户端复制配置要求的全部老历史。

### 第三批：驻留预算与可观测性

1. 增加提供方运行时软限额和明确的保护原因，不打断运行中回合、存活后台工作、权限请求或受保护任务。
2. 客户端正文预算同时考虑轮数与估算字节；活动生成区、索引与正文分开计量。
3. 全局预算分配不进入每次流式批次的全量扫描；按相关会话变更增量更新，批量处理淘汰。
4. 诊断展示驻留数、缓存字节估算、排队数、最长等待和淘汰原因，并覆盖已关闭运行时留下的缓存。
