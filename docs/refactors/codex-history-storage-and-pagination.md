# Codex CLI 长会话存储与分页对照

核查日期：2026-10-30。依据官方仓库 `openai/codex` 已发布的 [0.166.0](https://github.com/openai/codex/releases/tag/rust-v0.166.0)，固定提交 `6ff1e1ca3b30fc8b914720681fcf5fe62e95f856`。下面区分终端客户端、app-server 和存储层；不能由终端实现推断闭源 Codex 桌面 App 的具体渲染方式。

## 结论

Paseo 应优先处理全量重写和首次加载目标。用户通常同时使用不超过五个会话，本次不调整并发调度。

Codex 的有效做法有三项：新记录追加写入、首屏按可见高度与条目预算加载、回合和详细条目分开分页。仅模仿分页接口或把一页改小，不能消除 Paseo 当前重复读取、投影与传输整段历史的成本。

运行时释放后的缓存清理与冷恢复已经实现；随后实现了原生最新页先显示、完整历史静默后台读取，当前行为见 [时间线同步](../timeline-sync.md)。追加写入与可重建索引等其余存储建议尚未实施，没有引入数据库。

## 1. 写入：追加记录，等待明确的完成边界

[持久记录写入器](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/rollout/src/recorder.rs#L1029-L1047) 使用容量 256 的有界通道交给后台写入任务，队列满时发送者等待。文件以追加方式打开，每条新记录序列化为一行 JSON 后追加；普通追加不重新序列化已经保存的全部记录。

写入器保留尚未完成的条目，刷新和关闭经过同一写入顺序，失败通过确认结果返回并记录错误。这里的异步文件 `flush()` 不能直接解释为断电安全的 `fsync` 承诺。容量 256 是写入队列大小，和最多同时运行多少个 Agent 无关。

Paseo 当前每批追加会复制、校验、序列化并原子替换整个时间线 JSON。此前隔离样本约 43 MiB，每批仅增加一条短记录仍要处理约 43 MiB；详见[审计记录](session-memory-and-queue-audit.md)。25 毫秒合并窗口只能减少批数，不能消除每批的全量工作。

建议保留一条顺序写入路径，独立实现追加日志；原位修正、回退和时间线替换也必须有明确记录，不能只有简单 append。待写记录只有确认写入后才能移除，写入失败应阻止“释放完成”，保留重试所需数据。日志压实在独立的检查点上进行，不能每批重写快照。

## 2. CLI 加载目标：首屏预算不等于保留预算

[终端历史加载](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/tui/src/app_server_session/history.rs#L31-L100) 中，新格式初次先请求最近 5 个回合的头信息，条目每页最多 100 个。由应用掌控完整滚动区域的终端模式，初次条目加载按约三屏渲染行数计算，并把扫描预算限制为 400 个条目；该预算独立于随后阅读已经保留的历史量。

这不是“所有 Codex 模式最多五轮或四百条”。五轮是初始回合头页，加载条目时可补齐所需回合；传统终端滚动模式受其回流设置影响，完整读取、定位指定回合等用途也有单独规则。旧历史格式仍可能完整读取。源码按这些用途明确分支。

Paseo 当前初次可用后仍自动补齐配置的 50 轮，且这 50 轮包括所有处理过程。即使过程已经折叠、不挂载组件，其源记录仍会下载、解析、投影并驻留。这解释了“不展开也在付出成本”。

建议后续把两个概念拆开：

- **首次预取目标**：填满当前阅读区域及少量邻近区域，另加条目数和字节预算，不能为了隐藏过程无限续页。
- **已读历史保留预算**：控制用户实际读过的内容，滚动加载的一页不能刚加入就被全局轮次裁剪撤销；给正在阅读的窗口保留空间。

“加载 50 轮”的既有设置在本次保持不变。若改为按屏预取，应同步调整设置说明与测试，不把原来的轮次选项偷偷改成另一种含义。

## 3. 分页：新版有索引，旧版仍可能全量重放

[app-server 回合读取](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server/src/request_processors/thread_processor.rs#L3324-L3420) 明确分新旧历史格式：旧格式每次列回合仍读取并重放完整记录，再切响应页。它节省网络传输，但没有实现按页的存储读取。

新格式的回合接口可以只取回合头，或取用户消息和最终回复摘要；详细命令、过程与其他条目另走条目接口。两类接口默认 25、最多 100。显式请求完整回合仍会继续读取其全部条目，因此“使用新版接口”本身也不保证轻量。

[存储读取实现](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/thread-store/src/local/thread_history/read.rs#L108-L153) 从物化的回合、条目索引按游标取页；[索引定义](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/state/thread_history_migrations/0001_thread_history.sql) 包含回合序号、条目序号和已处理日志字节位置。它使用 SQLite，而非每次从头扫描 JSONL。

[索引构建](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/thread-store/src/local/thread_history_materialization_pipeline.rs#L1-L86) 把阻塞读取放到后台，按源字节和步骤数量分批，最多排队两批，提交后推进检查点。单条超大记录依然不能切成任意小块，不能忽略单条输出的大小。

审计时的 Codex 适配器已识别新旧格式并调用分页接口，但冷恢复仍完整收集原生历史后才返回首屏。后续已改为先显示官方最新页、其余历史静默后台读取，完整规范快照仍在全部核对后提交。Paseo 自己的 JSON 时间线仍按完整文档读取和投影，前端分 40 条尚未消除这些总成本。

建议先为 Paseo 时间线建立可重建的回合和条目位置索引，并把正文摘要与过程详情拆开读取。折叠过程仅加载入口、状态、耗时和必要摘要，展开时再取对应详情。不要把“已处理”入口、回合最终正文和后台仍在执行的工具状态一起删掉来换速度。

本仓库以文件持久化为约束。可以先评估追加文件加可重建的分段索引；若文件方案使回退、替换、搜索和一致性明显复杂，应单独评审 SQLite，而非在此次释放修复中直接更换存储架构。

## 4. 上滚：校验请求归属，再插入有界的新页

[CLI 上滚实现](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/tui/src/app/history_pagination.rs#L19-L144) 将滚动补载与历史覆盖视图共用一个待处理页。响应先核对会话与待处理游标，切换会话后的迟到页不继续插入；按条目身份处理重叠页，保留请求期间收到的实时消息，然后通知视口实际插入的范围。

Paseo 应继续保留已有稳定身份锚点和逐帧回归，进一步把一次补页的解析、投影和提交量限制住。终端单元与浏览器 DOM 的高度模型不同，不能直接移植终端坐标算法；字体或平滑滚动参数也无法抵消主线程一次处理大段历史造成的停顿。

## 5. 建议实施顺序与验收

1. **运行时释放**：本次已实现。等待写入结束后解除服务端和客户端可重建缓存，隔离迟到数据；重新进入恢复同一个原生会话。不调整并发上限，不删除磁盘记录、草稿和待发送消息。
2. **追加写入与可重建索引**：以既有长会话测每批序列化字节数和主线程耗时；一次短消息不能再随整段历史线性放大。验证写入失败、进程退出、回退、替换及索引重建后的数据一致性。
3. **首屏与详情分离**：分别测首屏请求数、传输字节、可交互时间；折叠过程不应预取全部工具输出。明确处理过程入口与导航索引的完整性。
4. **连续阅读预算**：快速上滚补页、展开大量过程、切换会话和实时消息并存时逐帧检查位置；不能只检查加载完成后的最终坐标，也不能把正在阅读的旧页立即裁掉。

并发调度暂不改。仅给并发数设上限，不能解决单个长会话每批全量重写和首屏过度预取。

## 6. 真实老会话打开耗时复核

复核日期：2026-10-31。样本为用户指定的 Codex 线程 `01a17c7d-8f81-7b40-84b2-d7f65d65ce1a`，对应本机 Paseo 智能体 `cda39583-3a54-4bfb-ac2e-495d789eb979`。本次只诊断与测量，没有修改产品加载行为、用户设置或会话正文，也没有启动模型回合、停止或重启主守护进程。

以下是首屏拆分前的诊断证据。随后按用户要求实现了官方原生最新页先显示、完整读取静默后台完成，不采用 Paseo 旧尾页替代，也不增加前端同步提示。新读取函数对同一真实线程测得原生最新 100 条约 672 毫秒；这不包含运行时恢复、桌面工具和界面渲染，不能当成端到端打开时间。

### 已确认的等待位置

本机桌面连接本机守护进程，使用直接连接。生产日志记录该次历史请求耗时 **31,543 毫秒**；提供方恢复完成日志距该请求返回约 675 毫秒。日志没有原生恢复各阶段的计时，不能据此把全部等待归到某个单独 RPC，也不能推断其他同时执行的目录订阅或远端 PR 查询是它的阻塞原因。

用当前源码的实际可执行文件解析、进程启动、JSON-RPC 传输与 `readCodexThread()`，启动独立只读 app-server，直接读取同一条真实线程。未调用 `thread/resume`、发送消息或修改归档状态，不占用原生线程的交互式写入者身份。读取接口可能维护 Codex 自己的索引，不承诺零磁盘写入。

原生详细记录包括 248 条用户消息、5,904 条推理、683 条助手消息、4,302 条命令、972 条文件变更，以及图片、搜索、压缩和子任务活动等。原生分页记录与合并后的 Paseo 规范记录口径不同，不能按两者条数差推断丢消息。

以上隔离测量没有覆盖原生 `thread/resume`、桌面工具初始化、完整历史投影与对齐、快照提交、前端下载和渲染，不能拿不同运行的时间简单相减并声称精确解释了其余约 8 秒。不过，仅真实原生历史读取就稳定消耗约 23.4 秒，足以确认主要等待发生在首屏响应前的服务端历史路径。

### 修复前为什么会等完整历史

`CodexAppServerAgentSession.connect()` 先准备目录、桌面工具、协作模式和技能，再用 `excludeTurns: true` 恢复原生运行时，随后仍完整读取主线程及子轨道。全部完成后，管理器才投影、对齐和提交历史，前端尾页请求最后才能返回。

因此设置的“打开时加载 100 轮”只限制后续客户端正文补载目标，不限制 Codex 适配器的全量读取。本样本没有卡在死循环，也没有证据证明请求结果丢失；当前约定让用户必须等全量核对完成，是可复现的首屏性能问题。此前修复的“100 轮未补齐”和“切回误开已耗尽历史边界”位于首个服务端响应之后，不能消除这段等待。

官方 0.166.0 的 [分页读取实现](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/thread-store/src/local/thread_history/read.rs#L163-L201) 使用物化索引，但每页仍解析当前线程的历史来源链，再按游标查询。[来源链解析](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/thread-store/src/local/rollout_lineage.rs#L50-L201) 会读取来源文件的元数据。不能把本样本描述成“Codex 的每个新格式分页都完整重放 JSONL”；也尚未单独量化来源链解析与 SQL 各自占本机每页耗时的比例。

### 已排除和可继续验证的方向

- **不改为逐回合完整读取。** 同一真实线程实验共请求 307 页，耗时 54,819 毫秒，读取条数仍为 12,596；它增加请求次数并明显变慢。该实验的完整序列化摘要也未与跨回合读取一致，未继续定位差异，不能认定两种结果完全等价，更不能直接替换生产路径。
- **不把页长继续增大。** 现有请求已经使用官方上限 100，超限参数不会自然变成更大的有效页面。
- **不通过保留已释放运行时和大缓存掩盖冷恢复。** 用户要求完整释放的行为继续保留；普通切换缓存保留与真正释放后的冷加载分别处理。
- **首屏与全量核对分开有实际测量依据。** 另一个独立 app-server 只读最近 5 个回合的摘要和最近 100 条详细记录，分别耗时 343、166 毫秒，总计约 510 毫秒，仍返回可继续加载的游标。这只是官方读取接口实验，没有恢复交互式运行时或接入真实界面，不能当成已经实现的 0.51 秒端到端打开速度；100 条也不能替代设置的 100 轮。

首屏就绪条件现已拆分：先取得官方原生最新页，使用户可以阅读；全量核对和配置的 100 轮补齐静默进行，不增加前端进度文案。局部原生尾页不写成完整持久快照，后台提交后按位置映射保留已有行身份，继续补齐索引与历史窗口。释放取消、失败重试以及首屏到完整历史的位置保持需要持续回归，不能只测最终页面。

实施时应记录原生恢复、主线程各类分页、子轨道、投影对齐、持久提交、首个响应和首屏渲染的分段耗时，再以本线程对照优化前后的首屏可读时间和总核对时间。并发限制、字体及滚动动画不作为本问题的首要改动。

## 7. 连续阅读仍慢的复核与下一步方案

复核日期：2026-10-31，仍使用第 6 节同一真实线程。以下是进一步测量和设计，**尚未实施**。现有渐进首屏改动仍在工作副本，未打包；本轮检查时未发现运行中的 Paseo 进程或监听中的本机 6767 服务，不能将这次原生接口实验称为已安装版的点击打开对照测试。

### 首屏拆分后仍保留的阻塞

1. `connect()` 在读取原生最新页之前，仍依次等待模型与配置、桌面工具、协作模式、技能及原生运行时恢复。上次的最新页约 672 毫秒只测了读取函数，不含这条前置链；不能据此宣称首屏已达到一秒。
2. 最新页之后仍完整读取全部原生条目。服务端对 `before` 请求不启用渐进读取，依赖完整历史的操作等待后台任务；客户端也在后台未就绪时关闭自动更早页边界。因而“先能看见尾页”还没有实现“立即连续上翻”。
3. 完整读取后，客户端按配置自动预取 100 轮的全部过程。折叠仅省去组件挂载，未省去工具输出的下载、JSON 解析、归并与布局模型计算。
4. 每页选取及导航索引构建仍会重新投影整段规范历史。现有虚拟列表和逐页让帧不等于数据处理已经局部化。不过本样本测得单页服务端投影加索引约 14–16 毫秒的最大值，尚不能把用户的一秒停顿全部归因于这项计算，前端仍需实际长任务与逐帧跟踪。

### 本机新增只读测量

使用现有可执行文件解析与 JSON-RPC 传输，启动独立 app-server，仅调用初始化、原生元数据、摘要和详细记录读取；没有恢复原生交互式线程、发送消息或触发模型生成。读取可能维护 Codex 自身索引，仍不承诺零磁盘写入。Paseo 快照只读，未改写真实历史或用户设置。

| 整个线程的原生摘要              | 592 毫秒，单次完整测量  | 3 页、260 个原生回合、248 条用户消息，共 325,277 字节                            |

最后一项在隔离 Node 进程中读取同一真实 Paseo 快照，调用当前页选择和索引函数模拟服务端逐页工作，不代表真实网络已传输了这些数据，也不包含客户端解析和渲染。65 页的计算及页结果序列化合计约 605–614 毫秒；不能将它直接相加到每次界面打开时间。

这组结果证明原生接口支持轻量、可连续的阅读路径。整个线程的用户消息和最终回复摘要只需约 318 KiB；最近 100 轮连同完整过程却需要约 17 MiB 的投影页结果。两者内容范围不同，不能据此宣传相同完整内容无损缩小了几十倍。

### 推荐实现：浏览页、过程详情与执行运行时分开

**第一步，真正按原生游标阅读。** 浏览首屏只等待只读连接初始化与本次原生数据；后续上翻继续使用原生游标读取所需页，不等全量扫描结束。模型目录、技能、桌面工具和交互式恢复退出首屏关键路径；发送消息时通过明确的执行就绪屏障等待这些能力，不假装已可执行。首屏仍禁止显示未经本次原生读取确认的 Paseo 旧尾页，也不增加同步文案。

**第二步，正文摘要与处理过程分离。** 使用官方 `thread/turns/list(itemsView: summary)` 展示用户消息、最终回复、回合状态和耗时；最近的活动过程读取有界详细页并接入真实生命周期事件。历史“已处理”展开后才用对应原生回合标识请求过程，继续分页和虚拟化，而非立即取完整长回合。收起过程不下载全部输出，不用伪造工具完成事件维持外观。

摘要不是完整历史。官方 [摘要读取](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/thread-store/src/local/thread_history/read.rs#L327-L366) 取首条用户消息及最终助手消息；中途说明、推理、工具和部分异常终止上下文不在其中。不能删除这些内容或把摘要标为完整快照。详情入口必须保留其可达性，未完成、失败、中断、插入消息及子任务要明确处理；没有最终回复的回合也不能仅剩一条用户气泡。原生回合与界面用户轮次继续分别建模，不把 100 个原生回合偷偷当作 100 用户轮。

**第三步，让页有稳定身份，不全量换代。** 浏览缓存以原生回合及条目标识保存实体，分页只加入新页、更新变化的条目；原生游标作为继续读取凭据，不预先伪造整段历史的全局序号。展开详情、补齐索引或后台核对不得重建全部已读消息和行高。回退、分支、外部客户端更新及缓存裁剪都要校验请求所属窗口，保留实时消息和阅读锚点。

**第四步，处理已存在的重复工作。** 页面、索引和处理过程模型按变化范围更新；必要的完整核对置于低优先级，不能阻塞用户请求的页。相邻阅读区域提前预取，限制条目数和总字节；单条超长正文不能直接截断，应走明确的分段展示。大文件写入仍按第 1 节评审追加记录和可重建索引，避免后台写入占满事件循环，但无需为静态阅读先更换数据库。

以上是依据公开接口和实测提出的二开设计，**不声称闭源 Codex App 内部使用了完全相同的实现**。公开 CLI 确实保留独立的原生分页游标、按可见行数控制初始预算，见其[历史加载实现](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/tui/src/app_server_session/history.rs#L28-L95)。不通过读取私有数据库、保留用户已释放的进程或移植上游 Paseo 代码实现提速。

### 验收目标

- 相同真实线程，分别记录冷打开、未释放切回和释放后重开，测点击到原生正文可读的端到端时间；以本机 1–2 秒为目标，不用接口耗时充当验收。
- 刻意暂停全量核对，首屏和连续更早页读取仍可用；外部 Codex 客户端新增内容必须进入原生最新页。
- 折叠历史只取阅读所需内容；扩大已有历史量不能让每页处理随整段历史线性增加，原生摘要不误写成完整磁盘记录。
- 连续快速滚动、逐页预取、展开长过程和实时回复并存时采集浏览器长任务与逐帧锚点；跟踪超过 50 毫秒的主线程任务及位置突变，不能仅检查最终坐标。
- 原有 100 用户轮目标与 3000 轮保留预算不擅自改值或改含义；若改成摘要预取和详情独立预算，需要同步调整设置说明并经用户确认。
- 释放后关闭所属连接，清除新增的页、详情、索引和行高缓存；迟到页不能恢复会话，也不为加速偷偷常驻已释放运行时。
