# 守护进程权限

守护进程使用语义权限授权身份主体。RPC 名称和协议命名空间本身不代表权限。

## 模型

```text
身份主体 -> 授权集合
    |
    +-- 由设备或服务凭证完成身份验证
    `-- 打开权限相同或更窄的会话
```

身份主体是守护进程长期授权的对象；凭证用于证明某个设备或服务代表该主体。两者保持分离后，系统才能轮换凭证、让同一主体连接多个设备，并在不虚构守护进程用户账号的情况下撤销 Hub 用户。

配对邀请既不是身份主体，也不是凭证。它是一个会过期且只能使用一次的交换入口，用于创建身份主体、凭证，并授予邀请签发者选定的权限。

## 权限表

| 权限                | 能力范围                                           |
| ------------------- | -------------------------------------------------- |
| `daemon.read`       | 守护进程状态、诊断、配置和提供方信息               |
| `daemon.manage`     | 重启、更新、配置修改、提供方、技能和插件           |
| `tunnel.manage`     | 中继、Hub、服务隧道和公共访问入口                  |
| `access.manage`     | 配对邀请、身份主体、凭证、授权和撤销               |
| `workspace.read`    | 项目、工作区、智能体、时间线、文件、差异和终端输出 |
| `workspace.write`   | 提示词、智能体控制、文件、终端、Git 操作和脚本     |
| `workspace.manage`  | 创建、重命名、归档和移除项目与工作区               |
| `automation.manage` | 定时任务、心跳和循环任务                           |
| `hub.execute`       | 由 Hub 拥有的任务执行生命周期                      |

智能体和终端共用工作区权限。两者都能够执行代码并修改工作区；把它们拆成两个写权限会虚构守护进程实际无法强制保证的隔离边界。

“所有者”“操作员”“查看者”只是界面预设，保存时必须展开为明确权限，不应作为角色持久化。新增权限不能静默扩大既有身份主体的授权。

权限只做累加式允许；缺少权限即拒绝操作，不引入“拒绝项优先”规则。

## 资源范围

当前权限作用于整个守护进程。未来的授权可以限定工作区或智能体，但操作分类仍由授权模块统一维护：

```ts
type Grant = {
  permission: Permission;
  resource: { kind: "daemon" } | { kind: "workspace"; ids: string[] };
};
```

能够转授权限的身份主体，只能授予自己已经拥有的能力。会话可以主动缩窄所属主体的授权，但不能扩大。

工作区范围授权要求每个携带资源的操作和每条出站观察都执行同一套边界检查。文件预览目前能够读取守护进程可访问的任意普通文件，因此在发布工作区级访问控制前，必须先为该入口增加资源范围校验。

## Hub

Hub 以服务身份主体完成验证。本地选择的授权决定它能否执行智能体、管理守护进程、管理隧道或管理访问权限。

Hub 的用户与角色标识始终只是外部系统的不透明主体。获得 `access.manage` 后，Hub 可以创建或撤销与之关联的守护进程身份主体；守护进程本身不解释账号、组织或角色语义。

Hub 注册和权限更新直接交换这些语义权限。包含 `hub.execution.*` 的旧 Hub 关系会在守护进程加载时一次性迁移为 `hub.execute`；新关系不会再把传输范围当作授权持久化。为兼容旧版本，新守护进程的状态响应暂时同时携带语义权限和旧 `scopes` 别名，但两者必须一致；两者同时缺失、旧范围未知或内容矛盾时，客户端必须明确拒绝该状态。
